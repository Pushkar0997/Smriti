## Question 1: Write-Ahead Logging (WAL) and Steal/No-Force Policy

**Question:** What is the Write-Ahead Logging (WAL) protocol in database storage engines, and why is the Steal/No-Force buffer management policy commonly paired with it?

**Answer:**
Write-Ahead Logging (WAL) is a fundamental durability protocol requiring that all log records representing changes to data pages must be flushed to non-volatile disk before the corresponding dirty data pages themselves are written to disk. Additionally, a transaction cannot be considered committed until its commit log record is safely written to disk.

WAL is commonly paired with the Steal/No-Force buffer management policy:
- Steal: The buffer manager is permitted to flush a dirty page containing uncommitted changes to disk if buffer frame space is urgently needed for another transaction. WAL guarantees atomicity despite "steal" because UNDO log records already reside on disk, allowing uncommitted modifications to be rolled back during crash recovery.
- No-Force: The buffer manager is not required to flush all dirty pages modified by a transaction to disk at commit time. WAL guarantees durability despite "no-force" because REDO log records already reside on disk, allowing committed changes to be reapplied during recovery.

Together, Steal/No-Force maximizes I/O throughput by allowing asynchronous page writes, while WAL guarantees ACID atomicity and durability via the ARIES recovery algorithm.

## Question 2: Write Skew Anomaly under Snapshot Isolation

**Question:** Explain the Multi-Version Concurrency Control (MVCC) snapshot isolation anomaly known as Write Skew, and provide a concrete example.

**Answer:**
Write Skew is a concurrency anomaly that can occur under Snapshot Isolation (SI) where two concurrent transactions read overlapping data sets, satisfy an invariant based on their individual snapshot reads, and then make disjoint updates that collectively violate the overall system invariant. Because their write sets do not intersect, standard Snapshot Isolation first-committer-wins conflict detection does not detect any conflict.

A classic concrete example is the "On-Call Doctors" scenario:
Invariant: At least one doctor must be actively on call at all times.
Initial state: Doctor A and Doctor B are both on call (count = 2).
Transaction 1 (Doctor A requesting leave): Reads the schedule, observes 2 doctors on call, determines the invariant (count >= 1) will hold after leaving, and updates Doctor A's status to inactive.
Transaction 2 (Doctor B requesting leave concurrently): Reads the same initial snapshot where 2 doctors are on call, determines the invariant will hold after leaving, and updates Doctor B's status to inactive.

Both transactions commit successfully because Transaction 1 modified Doctor A's record while Transaction 2 modified Doctor B's record (disjoint write sets). However, the final state leaves zero doctors on call, violating the system invariant. Preventing write skew requires Serializable Snapshot Isolation (SSI) or explicit locking (e.g., SELECT FOR UPDATE).

## Question 3: Comprehensive Analysis of ARIES Crash Recovery Protocol

**Question:** Provide an exhaustive analysis of the ARIES (Algorithms for Recovery and Isolation Exploiting Semantics) crash recovery protocol, explaining its three distinct recovery phases, the role of Log Sequence Numbers (LSNs), Compensation Log Records (CLRs), and the handling of checkpoints during system crashes.

**Answer:**
The ARIES (Algorithms for Recovery and Isolation Exploiting Semantics) crash recovery protocol is the canonical recovery algorithm for database systems employing steal/no-force buffer management and write-ahead logging. It provides physiological logging, repeating history during restart, and logging changes during undo to avoid cascading aborts.

### 1. Fundamental Data Structures and Log Sequence Numbers (LSNs)
ARIES coordinates recovery using monotonically increasing Log Sequence Numbers (LSNs) attached to every log record and page:
- PageLSN: Every database page in memory and disk contains the LSN of the log record describing the most recent update to that page.
- FlushedLSN: A global variable maintained in volatile memory tracking the maximum LSN written to persistent storage. The WAL invariant requires PageLSN <= FlushedLSN before a dirty page is written to disk.
- Transaction Table (TT): Tracks all active transactions, their status (Running, Committing, Aborting), and their lastLSN (the LSN of the most recent log record generated by that transaction).
- Dirty Page Table (DPT): Tracks all dirty pages currently residing in the buffer pool, mapping each page ID to its recLSN (the earliest LSN whose update has not yet been flushed to disk for that page).

### 2. Checkpointing Mechanics
ARIES utilizes fuzzy non-blocking checkpointing. A checkpoint does not force dirty pages to disk; instead:
1. A checkpoint_begin record is appended to the log.
2. The current contents of the Transaction Table and Dirty Page Table are captured in memory.
3. A checkpoint_end record containing the copied TT and DPT is written to the log.
4. The Master Record stored at a well-known disk location is atomically updated to point to the checkpoint_begin record.

### 3. Phase 1: The Analysis Phase
Upon system restart following a crash, the Analysis phase begins by locating the most recent checkpoint via the Master Record:
- The log is scanned forward from the checkpoint_begin record up to the end of the log.
- The Transaction Table and Dirty Page Table are reconstructed to reflect the exact state of volatile memory at the precise moment of failure.
- When an end log record is encountered, the corresponding transaction is removed from the TT.
- When an update log record for a page not yet in the DPT is found, that page is added to the DPT with recLSN equal to the update's LSN.
- The Analysis phase determines the set of "loser" transactions (active transactions that had not committed before the crash) and identifies smallestRecLSN (the minimum recLSN across all pages in the DPT), which establishes the exact starting point for Phase 2.

### 4. Phase 2: The Redo Phase
The Redo phase re-establishes the exact database state that existed immediately prior to the crash by repeating history:
- The log is scanned forward beginning from smallestRecLSN up to the end of the log.
- For every update record and Compensation Log Record (CLR) encountered, the engine determines whether the update must be reapplied. Redo is skipped only if:
  1. The page is not listed in the DPT, or
  2. The record's LSN is strictly less than the page's recLSN in the DPT, or
  3. The page is read from disk and its PageLSN on disk is already greater than or equal to the record's LSN.
- Otherwise, the action is reapplied in memory, and the page's PageLSN is updated to the record's LSN. At the completion of the Redo phase, the database state exactly matches the state at the moment of failure.

### 5. Phase 3: The Undo Phase
The Undo phase reverses the actions of all loser transactions that were active at the time of failure:
- A priority queue of lastLSN values for all active loser transactions is maintained, ordered descending by LSN.
- The log is scanned backward, processing the highest LSN in the queue.
- If the record is a regular update, the modification is undone on the corresponding page, and a Compensation Log Record (CLR) is written to the log. The CLR contains an UndoNextLSN pointer pointing to the PrevLSN of the undone record. The page's PageLSN is updated to the CLR's LSN.
- If the record is a CLR, no undo operation is performed on the page; instead, the traversal jumps directly to the record's UndoNextLSN, completely bypassing already-undone actions. This critical design guarantee ensures that crashes occurring during recovery never repeat undo operations and bound recovery time.
- When an undo operation reaches the beginning of a transaction, a transaction_end record is logged, and the transaction is removed from the loser set. When the queue becomes empty, recovery is complete and the database opens for normal operations.

## Question 4: Two-Phase Locking (2PL) Variants and Concurrency Guarantees

**Question:** How does the Two-Phase Locking (2PL) protocol guarantee serializability, and what distinguishes Strict 2PL (S2PL) and Rigorous 2PL (R2PL) from Basic 2PL?

**Answer:**
The Two-Phase Locking (2PL) protocol guarantees conflict serializability by enforcing that each transaction acquires and releases locks in two distinct, monotonic phases:
1. Growing Phase: The transaction may acquire shared (read) or exclusive (write) locks on data items, but cannot release any lock.
2. Shrinking Phase: The transaction may release locks, but cannot acquire any new lock under any circumstance.

The point at which a transaction acquires its final lock is its "lock point." Conflict serializability is guaranteed because transactions serialize according to the chronological order of their lock points, preventing cycles in the precedence (serialization) graph.

The variants differ in how locks are released during the shrinking phase:
- Basic 2PL: Locks can be released as soon as an item is no longer needed, during the shrinking phase. While conflict-serializable, Basic 2PL is vulnerable to cascading aborts: if Transaction T1 reads data modified by uncommitted Transaction T0, and T0 aborts after releasing its locks, T1 must also abort.
- Strict 2PL (S2PL): All exclusive (write) locks must be held continuously until the transaction terminates (commits or aborts). Shared (read) locks may be released earlier. S2PL guarantees Recoverability and Avoids Cascading Aborts (ACA) because uncommitted writes are never exposed to concurrent transactions.
- Rigorous 2PL (R2PL): Both shared (read) and exclusive (write) locks must be held continuously until transaction termination. In R2PL, the shrinking phase occurs in a single atomic step at commit/abort time. R2PL guarantees that the serialization order is identical to the transaction commit order, eliminating all cascading aborts at the expense of reduced concurrency.

## Question 5: Dense vs Sparse Indexing Trade-offs and Viability Conditions

**Question:** Explain the difference between dense and sparse indexing in database storage, and discuss the architectural conditions required for sparse indexing to be viable.

**Answer:**
In database storage architectures, dense and sparse indexing represent contrasting trade-offs between index size and search performance:
- Dense Index: Contains an explicit index entry (search key value and record pointer) for every single search key value present in the data file. In a clustered dense index, duplicate keys may point to the first occurrence. In an unclustered secondary index, every individual record has a dedicated index entry.
- Sparse Index: Contains index entries for only a subset of search key values in the data file, typically storing one index entry per disk block (data page), representing the lowest or highest key value on that block.

Architectural viability conditions for sparse indexing:
1. Physical Ordering: The underlying data file must be physically sorted on the search key. If the records are not sequentially ordered on disk according to the search key, sparse indexing cannot bracket records into ranges, making it impossible to locate records without a dense scan.
2. Clustered Layout: Sparse indexing is strictly viable only for the primary/clustering index. Secondary indexes cannot be sparse because secondary attributes do not dictate physical disk placement.
3. Block-Level Navigation: The search algorithm uses the sparse index to locate the largest index key less than or equal to the target key, identifying the specific disk block where the record must reside if it exists. The system then fetches that single disk block and conducts an in-memory binary or linear search.

Trade-offs: Dense indexes enable index-only scans (answering queries without touching data pages) and work on unsorted secondary attributes, but require significantly more storage and memory. Sparse indexes require a fraction of the index space (easily fitting entirely within the buffer cache) and have lower maintenance overhead during page splits, at the cost of always requiring at least one disk block read to inspect records.
